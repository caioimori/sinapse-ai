# Story 10.47 — Generalize grounding semantico como opt-in BYO

## Story

**As a** novo usuário do SINAPSE-AI rodando `npx sinapse-ai install`,
**I want** o framework me oferecer (opcionalmente) configurar meu próprio vault de notas, design system de projeto e brandbook,
**so that** eu acesse o grounding semântico — diferencial real do SINAPSE vs frameworks concorrentes — sem precisar herdar a config pessoal de outro usuário ou aceitar paths hardcoded que só funcionam pro autor do framework.

## Context

Análise competitiva (privada, scratch) comparando SINAPSE-AI × `aiox-core` (concorrente direto, 2.8k stars, GA shipped) revelou que o **grounding semântico** (vault → context injection do Second Brain; DS → design system per-project; brand → brandbook lookup) é o **único diferencial real** que nenhum framework PT-BR concorrente entrega. Aiox tem hooks de git, mas não tem grounding semântico de domínio.

**Problema atual:** o grounding hoje vive 100% em `~/.claude/` global do Caio (autor do framework). Não está shipado no repo `sinapse-ai`. Confirmado por inspeção em 2026-04-30:
- `.sinapse-ai/hooks/` tem apenas `ids-post-commit.js`, `ids-pre-push.js`, `unified/`
- Nenhum arquivo `vault-grounding`, `design-system-grounding` ou `brand-grounding` existe no repo
- `~/.claude/rules/vault-grounding.md`, `~/.claude/rules/design-system-grounding.md` são globais do Caio, não distribuídos via npm

**Restrição de escopo (memory rule `feedback_framework_vs_personal_config.md`):** mudanças aplicam APENAS no repo `sinapse-ai` distribuído via npm. `~/.claude/` global do Caio fica intocado — ele usa essa config diariamente em múltiplos projetos.

**Severidade P1:** não bloqueia GA por código quebrado, mas bloqueia mensagem de produto. Sem isso, README e onboarding não conseguem destacar o moat real porque ele só funciona pro Caio.

## Acceptance Criteria

1. **Given** um usuário rodando `npx sinapse-ai install` em ambiente interativo, **when** o wizard avança após coletar idioma + LLM (Story 10.46), **then** ele apresenta 3 perguntas opcionais de grounding (vault path, design system, brand profile), cada uma com opção explícita de "pular" e mensagem clara de que o skip ativa fallback genérico.

2. **Given** o usuário responde com path de vault válido, **when** a instalação completa, **then** o arquivo de configuração local em `~/.claude/sinapse-ai-config.yaml` (ou equivalente sob `SINAPSE_HOME`) registra esse path, e um hook shipado pelo framework (`.sinapse-ai/hooks/vault-grounding.cjs` ou similar) lê essa config e injeta contexto do vault em mensagens do usuário. Sem o config, hook é no-op (não injeta nada).

3. **Given** o usuário pula a pergunta de DS, **when** o wizard finaliza, **then** o framework usa o `fallback.high-quality-defaults` já presente em `ds-routing.json` (validar via grep que esse fallback realmente existe na config padrão shipada).

4. **Given** o usuário pula a pergunta de brand, **when** instalação completa, **then** brand-grounding fica desativado (no-op) e nenhum erro de "brandbook não encontrado" ocorre.

5. **Given** o repo após esta story, **when** alguém faz `find packages/installer/templates -type f`, **then** existem 3 arquivos exemplo:
   - `packages/installer/templates/vault-routing.example.json` — schema mínimo de config de vault
   - `packages/installer/templates/ds-routing.example.json` — schema mínimo de config de DS
   - `packages/installer/templates/brand-routing.example.json` — schema mínimo de config de brand
   Cada arquivo contém comentários explicando os campos e exemplos preenchidos genéricos (não SINAPSE-específicos).

6. **Given** o repo após esta story, **when** alguém abre `README.md`, **then** existe uma seção "Grounding semântico (opt-in)" nas primeiras 30 linhas (ou no segundo bloco visível pós-tagline) explicando que vault/DS/brand são diferenciais opt-in do SINAPSE, com link pra guide detalhado em `docs/guides/grounding-setup.md`.

7. **Given** o repo após esta story, **when** alguém abre `docs/guides/grounding-setup.md`, **then** o guia documenta: (a) o que é cada um dos 3 grounding types, (b) quando faz sentido habilitar cada um, (c) como configurar manualmente sem o wizard (editar `~/.claude/sinapse-ai-config.yaml`), (d) como o fallback funciona quando não configurado.

8. **Given** uma instalação existente (Story 10.20 upsert), **when** o usuário roda `npx sinapse-ai install` sem `--reconfigure`, **then** o wizard NÃO re-pergunta vault/DS/brand se já estão configurados (preserva idempotência). Com `--reconfigure`, re-pergunta.

9. **Given** o PR final desta story, **when** o reviewer roda `git diff main...HEAD --name-only`, **then** **zero entradas** começam com `.claude/`, `~/.claude/`, ou apontam pra arquivos pessoais do autor do framework. Toda mudança vive sob `packages/`, `bin/`, `docs/`, `README.md`, ou `.sinapse-ai/hooks/` (escopo do repo). [Reformulado pela @product-lead — `~/.claude/` está fora do repo, então `git diff` original não testaria nada; agora a verificação é via inspeção do diff do PR.]

10. **Given** os hooks shipados pelo framework, **when** instalados em uma máquina sem Second Brain / sem DS / sem brandbook configurado, **then** eles não emitem warnings ruidosos nem erros. No máximo um log informativo no nível `debug` (silenciado por default).

| Hooks novos quebrarem instalações existentes | Default explícito é no-op. Hook só age se `~/.claude/sinapse-ai-config.yaml` existir E tiver a seção correspondente preenchida |

O hook shipado lê `~/.claude/sinapse-ai-config.yaml` (criado pelo installer); a regra global do Caio lê `~/.claude/vault-routing.json`. | Confusão de usuário sobre "qual é o diferencial vs concorrente" | Mitigar via README + guide claros. Tagline do README cita "grounding semântico opt-in" como destaque |
| Shipar hooks mal testados em CI | Test matrix nova cobrindo: install com vault preenchido, install com vault vazio, install em CI (skip todos), upsert sem `--reconfigure` |
| `~/.claude/sinapse-ai-config.yaml` colidir com config existente da Story 10.46 | Story 10.46 já grava language/LLM em `~/.claude/settings.json` (linha 371 de bin/cli.js, fora do escopo desta story). Esta story cria arquivo separado pra grounding — sem conflito |
